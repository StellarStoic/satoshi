    Lightning guide

    Your own address, your own domain

    A Lightning address looks like an email address. It can carry your domain while the payments still land in the wallet you already use — and you can change wallets without changing the address.

    What a Lightning address really is

    An address such as yourname@getalby.com is not an inbox. It is a name a wallet turns into a URL, fetches, and reads a small JSON document from. For an address name@domain.tld the URL is always the same shape:

    https://domain.tld/.well-known/lnurlp/name

    Ask for that URL and the wallet answers with a pay request: the smallest and largest amounts it will take, a line of text saying who is being paid, and a callback — the address a wallet calls, with an amount, to get an actual invoice. A live answer, abbreviated:

    {
  "callback": "https://minibits.cash/.well-known/lnurlp/yourname",
  "minSendable": 1000,
  "maxSendable": 1000000000,
  "metadata": "[[\"text/plain\",\"Pay to yourname@minibits.cash with Lightning.\"],[\"text/identifier\",\"yourname@minibits.cash\"]]",
  "commentAllowed": 100,
  "allowsNostr": true,
  "tag": "payRequest"
}

    Amounts are in millisatoshis, so minSendable 1000 is one sat and maxSendable 1000000000 is one million sats.

    The address is a pointer and nothing else. Whoever answers that one URL decides where the money goes. That is the whole trick: the name can be yours while the URL is answered by your wallet — or by a copy of your wallet's answer sitting on your own server.

    Each wallet below has its own section: what its pay request looks like, the exact file to save, the exact redirect line, and how to check the result. Jump to Alby, Wallet of Satoshi, Minibits or Coinos, or read the common part first.

    Why bother

    • The address outlives the wallet. Move from one provider to another and the address in your podcast notes, your shop and your profile stays the same.
    • Your identity is your domain. No provider can rename you, retire your identifier, or take the name away.
    • It pairs with a NIP-05 name. The same local part can be your Nostr identity and your payment address, so people learn one string instead of two.

    The part that is the same for every wallet

    Three things never change between wallets, so they belong here once and each wallet section will only refer to them.

    The domain has to answer first. If it already serves a site, skip this. If not, point it at the host that will hold the file — for GitHub Pages that is four A records on the apex, or a CNAME on a subdomain:

    185.199.108.153
185.199.109.153
185.199.110.153
185.199.111.153

    Use the lowest TTL your DNS provider allows and wait for propagation, which can take minutes or hours. Then enter the domain under the repository's Settings → Pages and switch on Enforce HTTPS once the certificate is issued.

    The file method is always the same two steps. Save the wallet's answer as a plain text file named after the address you want to hand out — for two@example.com the file is named two, with no extension — and put it at .well-known/lnurlp/two, so it is reachable at https://example.com/.well-known/lnurlp/two. If the host builds the site with a static generator, tell it to publish the folder, because a leading dot means many generators skip it by default:

    include:
  - .well-known

    Serve it over HTTPS, and use a temporary redirect when you redirect. 302 or 307, never 301: a permanent redirect invites clients and proxies to remember the target indefinitely, which is the last thing you want the day you change wallets. And allow other origins, because a wallet inside a web page reads this URL from a browser and a browser refuses a cross-origin read without the right header. On Apache that grant can be scoped to this one path:

    Redirect 302 /.well-known/lnurlp/two https://getalby.com/.well-known/lnurlp/yourname

<If "%{REQUEST_URI} =~ m#^/.well-known/lnurlp/#">
    Header always set Access-Control-Allow-Origin "*"
</If>

    Alby

    Addresses look like yourname@getalby.com. The callback stays on the same domain as the address, which makes Alby the most straightforward of the four. Its answer also carries payerData, describing which sender details the account welcomes, so a client may ask for a name or an email before paying.

    Pay request
    https://getalby.com/.well-known/lnurlp/yourname
    Range
    1 sat to 10,000,000 sats, read from an account that accepts payments
    Comments
    Up to 255 characters
    Zaps
    allowsNostr true with a nostrPubkey
    Callback
    https://getalby.com/lnurlp/yourname/callback — same domain

    As a file. Open the pay request above in a browser, save the JSON as two, and place it as described in the common steps. Nothing needs editing: the callback inside already points at Alby.

    As a redirect. Inside the server block for your domain:

    location = /.well-known/lnurlp/two {
    return 302 https://getalby.com/.well-known/lnurlp/yourname;
    add_header Access-Control-Allow-Origin "*";
}

    Check it. Fetch your own address, then reload nginx:

    curl -s https://example.com/.well-known/lnurlp/two
sudo nginx -t && sudo systemctl reload nginx

    Wallet of Satoshi

    Addresses look like yourname@walletofsatoshi.com. One thing here is worth understanding rather than copying blindly: the callback does not stay on walletofsatoshi.com. It points at livingroomofsatoshi.com with a long account identifier in the path — a different host, run by the same service.

    Pay request
    https://walletofsatoshi.com/.well-known/lnurlp/yourname
    Range
    1 sat to 100,000,000 sats per payment
    Comments
    Up to 255 characters
    Zaps
    allowsNostr true with a nostrPubkey
    Callback
    livingroomofsatoshi.com with a per-account id

    As a file. Copy the answer whole. That is not politeness — rebuilding it from what you remember is how you write the wrong host, and an address whose callback points nowhere answers with a pay request that can never produce an invoice.

    As a redirect. The same shape, a different target:

    location = /.well-known/lnurlp/two {
    return 302 https://walletofsatoshi.com/.well-known/lnurlp/yourname;
    add_header Access-Control-Allow-Origin "*";
}

    Check it. Read the metadata line after fetching your own address. It should name the account that will actually receive the money; if it names someone else, the copy or the redirect points at the wrong place.

    curl -s https://example.com/.well-known/lnurlp/two | head -c 400

    Minibits

    Addresses look like yourname@minibits.cash. Minibits is an ecash wallet, so a payment arrives over Lightning and lands as ecash — the address is the front door, not the wallet. Its callback is the same path it was fetched from, the simplest case here.

    Pay request
    https://minibits.cash/.well-known/lnurlp/yourname
    Range
    1 sat to 1,000,000 sats per payment
    Comments
    Up to 100 characters
    Zaps
    allowsNostr true with a nostrPubkey
    Callback
    The same path on minibits.cash

    As a file. Save the JSON as two. The callback is on the same path, so a copy keeps working for as long as Minibits keeps its endpoint shape.

    As a redirect. The same shape again:

    location = /.well-known/lnurlp/two {
    return 302 https://minibits.cash/.well-known/lnurlp/yourname;
    add_header Access-Control-Allow-Origin "*";
}

    Check it. Follow the redirect once and require JSON back, not a web page:

    curl -sL https://example.com/.well-known/lnurlp/two | head -c 300

    Coinos

    Addresses look like yourname@coinos.io. Coinos is where the callback gets interesting: it moves to another host and it arrives with a query string already attached.

    "callback": "https://names.coinos.io/lnurlp/yourname/cb?domain=coinos.io"

    That ?domain= is the reason to read the callback instead of rebuilding it. A client that appends ?amount=… to that address produces two question marks and a dead URL; the amount has to join with &amount=…. Every wallet gets this right because it treats the callback as an address and adds a parameter; a person editing by hand does not.

    Pay request
    https://coinos.io/.well-known/lnurlp/yourname
    Range
    1 sat to 500,000 sats per payment
    Comments
    Up to 200 characters
    Zaps
    allowsNostr true with a nostrPubkey
    Callback
    names.coinos.io, carrying ?domain=coinos.io already
    Also on DNS
    publishes a _bitcoin-payment record, so the DNS route below works for it

    As a file. Save the answer exactly as it comes. If you edit the callback to add an amount while copying, you have broken it.

    As a redirect. The target is Coinos' own pay request, not the callback — the amount is added later, by the paying wallet:

    location = /.well-known/lnurlp/two {
    return 302 https://coinos.io/.well-known/lnurlp/yourname;
    add_header Access-Control-Allow-Origin "*";
}

    Check it. Your address should answer, and the callback inside should still carry both the host and the query string:

    curl -s https://example.com/.well-known/lnurlp/two

    Coinos on DNS, without a file or a server

    Coinos also publishes the newer kind of record, which lets a wallet find the payment instruction in DNS instead of over HTTP. That is BIP 353: for two@example.com a wallet asks for the TXT record at two._bitcoin-payment.example.com. You do not author that record — you chain a CNAME to Coinos' own:

    two._bitcoin-payment.example.com.  CNAME  yourname.user._bitcoin-payment.coinos.io.

    In a Cloudflare-style panel the record goes in as two._bitcoin-payment with that target, and it must stay DNS-only. A proxied record is a web record, and there is no web here.

    Two conditions decide whether any wallet can use it:

    • Ask the target, do not assume it. Name it exactly as Coinos documents it, then check the chain yourself:
    dig +short CNAME two._bitcoin-payment.example.com
dig +short TXT   two._bitcoin-payment.example.com
    • DNSSEC has to be real, not just switched on. A wallet trusts this answer only if it can validate the chain, so the zone must be signed and the DS record must be published at your registrar. Turning DNSSEC on in the DNS panel is half the job; the DS entry at the registrar is the other half. Until both exist the answer is unsigned as far as a validator is concerned, and a BIP-353 wallet will ignore the record. Any resolver will tell you which state you are in:
    dig +short DS example.com

    Treat the DNS route as a bonus on top of the address, not a replacement: far fewer wallets resolve DNS than read a /.well-known/ address, so the file or the redirect is what most of your listeners will use.

    File, redirect, or DNS

    • A file works on any host, including one that serves nothing but files. It is also a snapshot: it keeps the callback it had on the day you copied it, so if the wallet reshapes its endpoint the address goes quiet and the file needs refreshing.
    • A redirect cannot go stale, because every request asks the wallet itself. Prefer it whenever you have a server.
    • A DNS record needs no server and no file, but the fewest wallets read it, and it only exists where the wallet publishes such a record at all.

    One caution about every number quoted above: it belongs to the account, not to the wallet. A different name on the same service can allow a different range, and an account that has not been set up to receive reports maxSendable: 0, which means nobody can pay it. Read the range from your own endpoint before quoting it to anyone.

    Before you hand the address out

    1. Fetch your own address from outside your head: 
      curl -s https://example.com/.well-known/lnurlp/two
    2. Read the metadata line. It should name the account that will actually receive the money. If it names someone else, the copy or the redirect points at the wrong endpoint.
    3. Check the status. curl -sI should show 200 for a file or 302 for a redirect, and the body should be JSON rather than HTML.
    4. Pay it. Send the smallest amount your wallet allows and confirm it arrives, watching which name the invoice describes — that is where the money goes.
    5. Try it in one browser-based client as well as one app. That is the only way to catch a missing CORS header before a stranger does.

    What tends to break

    • A saved copy is a snapshot. The file keeps the callback it had on the day you copied it. A redirect does not have this problem, which is why it is the better default when you have a server.
    • Not every provider's JSON can be copied. Copy the answer only if its callback is a full URL, as all four wallets here serve. Watch for a callback generated per request, or one that needs something you do not have; then only a redirect works.
    • Plain HTTP does not count. Clients require HTTPS, so the certificate has to be right on the host answering /.well-known/, not just on the wallet's side.
    • Dot folders get dropped. Static generators routinely ignore .well-known unless told otherwise. Check the live URL, not the file in your editor.
    • The path must not be taken. .well-known/lnurlp/two is a path like any other; if your host answers it with a page instead of the file, wallets read HTML and fail.
    • Lowercase. Addresses are matched as written. Two@example.com and two@example.com ask for two different files on a case-sensitive host.

    Where this comes from: the address-to-URL rule is LUD-16, the shape of a pay request is LUD-06, and the DNS route is BIP 353.
